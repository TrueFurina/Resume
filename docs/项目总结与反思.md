# 项目深度总结与反思

**物理学科智能排课选课智能体系统**（Solo 版）
日期：2026-08-16 ｜ 作者：张敏杰（需求调研 + 独立开发）

---

## 一、项目历程回顾（7/20 → 8/16）

### 阶段一：盲目启动（7/20-7/23）

- 最初拿到题目"物理学科智能排课选课智能体系统"，我第一时间埋头写代码：CRUD 排课系统、排课引擎、学生选课页面
- **问题**：没有验证需求就动手，方向错了
- **教训**：产品经理的基本功是"判断该不该做"，而不是"快速做出来"

### 阶段二：需求质疑与验证（7/24-7/26）

- 我作为资深产品经理，提出核心质疑："这个项目有没有需求？"
- 逐一验证：
  - 学生选课？→ 公共必修课强制必选，**无需求**
  - 签到？→ 学习通已有，**无需求**
  - 实验报告？→ 手写是教学要求，**无需求**
  - 排课？→ 论文证明教务系统管不了实验排课，**有痛点**
- 调研论文（安徽工业大学、北邮、重庆大学等）确认：实验排课是"二次分配"问题，一处调整引发连锁冲突
- **结论**：需求存在，但比题目想象的小得多——核心痛点是"调课冲突协调"

### 阶段三：收敛为调课最小闭环（7/26-8/2）

- 砍掉 8 项需求（学生端/签到/报告/规则知识库/自动排课/教务对接等）
- 确定最小闭环：教师说"第六周的课上不了，调到下周"→ 系统筛出可用时段 → 教师选择 → 管理员审批
- 关键转变：从"冲突检测"（用户指定时段再校验）到"空闲时段筛选"（筛掉冲突的，剩下就是可选的）——这是从系统思维到用户思维的转变

### 阶段四：评审反馈与迭代（8/15）

中期验收评审（胡锐锋、王铮、任成森）指出：

| 评审意见 | 我的应对 |
|---------|---------|
| 用户一进来"两眼空白"，不知道有哪些课 | 增加身份选择 + 我的课程列表（可调/不可调） |
| 参考火车票改签交互 | 改为"先看课程 → 再选时间"两步式 |
| 信息透传不足 | 每个被排除时段标注原因 |
| 纯自由文本缺信息 | 模板表单为主 + 多轮追问 |
| 权限身份问题 | 教师/管理员角色 + 审批流 |
| 四大核心模块缺一不可 | 补齐排课/选课/调课/辅导 |

### 阶段五：LLM 接入与四大模块（8/16，最后一天）

- 接入律动基元（TokenRhythm）LLM：意图解析、AI候选方案、选课咨询、实验辅导、多轮追问
- 补齐四大模块：排课（冲突筛选+候选）、选课（LLM咨询）、调课（核心闭环）、辅导（LLM咨询）
- 完成全部文档：技术架构 V1.0、PRD V1.0、产品使用指南、演示脚本

## 二、做对了什么

### 1. 坚持需求验证，不盲目开发

整个项目最正确的决定是**在动手前质疑需求**。虽然最终被要求做四大模块，但需求验证的过程让我：
- 砍掉了真正无意义的功能（学生端、签到、报告）
- 把项目聚焦到"调课冲突协调"这个真实痛点上
- 在答辩时能诚实说出"哪些需求不存在、为什么"，这本身就是调研能力的体现

### 2. "做减法"的产品判断力

评审认可了我的减法思路："用做减法的思路把全局调度降级为局部冲突规避"。从"排课选课智能体"这个宏大题目的泥潭里，找到"调课"这个最小可验证的切口，是产品经理的核心能力。

### 3. 论文与真实数据支撑

用论文证明"教务系统管不了实验排课"、用自己的课表和学校实验安排表做真实数据验证——这让项目不是空中楼阁，每一步都有依据。

### 4. 快速响应评审意见

评审提出的每一条意见（引导缺失、信息透传、火车票改签、模板优先、审批流、四大模块）都在当天或几天内落实，说明执行力在线。

### 5. 技术上的正确选择

- **规则引擎兜底 + LLM 增强**：核心流程不依赖 LLM 稳定性，演示可靠
- **数据驱动**：各校上传总表即可用，天然可推广
- **时间归一化**：解决了 Excel 12 种时间格式导致冲突比对失效的隐藏 bug

## 三、做错了什么 / 不足

### 1. 一开始盲目写代码（最大的错误）

**错误**：7/20 拿到题目就直接写 CRUD 排课系统、排课引擎、选课页面——完全没有先做需求分析。

**代价**：写了大量无用的代码（课程管理、教师管理、学生选课），最后全部废弃重写。

**反思**：作为产品经理，第一反应应该是"验证需求"而不是"写代码"。这个错误浪费了约 1/3 的项目时间。

### 2. 与组长协作脱节

**错误**：需求分歧（我认为只需调课，组长做完整系统）导致各做各的，没有及时对齐。

**代价**：评审时被指出"项目内部协作已出现脱节"，最终走向 Solo 提交。

**反思**：团队协作中，分歧应该尽早沟通对齐，而不是各自为战。虽然 Solo 结果不算差，但这不是主动选择，而是被动结果。

### 3. 时间管理失控

**错误**：前期大量时间花在错误方向的开发和反复调试上（比如服务反复启动失败、PDF 解析器的过度调试），导致最后一天极限冲刺。

**代价**：最后一天赶工，部分功能（申请单持久化、多学生课表、PDF完美解析）未能完善。

**反思**：时间应该优先投入在"核心闭环 + 文档"，而不是边角功能。评审也提醒过"先跑通业务逻辑，不要过早投入 UI"。

### 4. 对"四大模块"的判断有偏差

**错误**：我一直坚持"调课就足够了"，对评审强调的"四大模块缺一不可"理解不足。

**代价**：虽然最终补齐了四大模块，但选课/辅导只是 LLM 咨询的轻量实现，深度不够。

**反思**：评审的"四大模块"不是让每个模块都做完整系统，而是要求产品具备完整的业务能力覆盖。我之前的"砍需求"是对的，但对"必须展示完整业务闭环"理解不够——**砍掉的是伪需求，不能砍掉业务闭环**。

### 5. 技术细节的反复折腾

- 服务启动问题反复出现（bash 进程被清理、IPv4/IPv6 监听问题），浪费了不少时间
- PDF 解析器追求完美解析教务课表，投入产出比低（最后用结构化数据替代）
- 这些是"技术洁癖"的表现，应该更早接受"够用就好"

## 四、核心认知升级

### 1. "没需求" vs "需求方不是我"

项目中最纠结的问题是"这个项目到底有没有需求"。最终答案是：

> **学生视角没需求（强制必修不需要选课），但排课管理者视角有需求（论文证明实验排课靠人工协调）。我没采访到教务员，所以无法 100% 确认，但证据指向需求存在。**

这让我明白：**"我没看到需求"不等于"没有需求"，可能是需求方不是我的用户视角。**

### 2. "做减法"与"业务闭环"的平衡

- 做减法：砍掉伪需求（签到、报告、选课系统）——对
- 业务闭环：排课/选课/调课/辅导四大能力都要能演示——也对

**两者不矛盾：砍掉的是"不必要的功能"，保留的是"业务闭环的完整性"。**

### 3. 规则引擎与 LLM 的正确关系

评审质疑"AI 价值体现不足"。我的结论：

> **LLM 应该增强体验（意图解析、候选方案、咨询问答），规则引擎保证正确性（冲突筛选）。不能为了 AI 而 AI，也不能不用 AI。**

这正是"AI 加"和"加 AI"的区别——先把规则引擎跑通（加 AI 的底座），再让 AI 提升体验。

### 4. 评审是产品的镜子

中期评审的每条意见都指向真实问题：
- "用户是懵的" → 产品缺乏引导设计
- "信息透传不足" → 产品的可解释性缺失
- "火车票改签" → 用成熟场景类比抽象产品

**评审不是在找茬，是在帮你发现产品设计的盲区。**

## 五、给未来的建议

### 对项目本身

1. **申请单持久化**：内存 → SQLite，让审批数据可追溯
2. **多学生课表**：批量导入，支持老师教多个班的真实场景
3. **排课自动生成**：从"冲突筛选"升级到"约束求解自动排课"
4. **知识库 RAG**：实验讲义/规范接入，增强辅导模块的专业性
5. **用户调研**：如果能采访到教务员，用一手反馈验证需求

### 对个人成长

1. **先验证需求，再写代码**——这是这次项目最贵的教训
2. **团队协作要及时对齐**，分歧不能变成各自为战
3. **时间管理**：核心闭环优先，边角功能最后，文档贯穿始终
4. **接受"够用就好"**：PDF 完美解析、服务稳定性这些"技术洁癖"要克制
5. **产品经理的价值在"判断"**：判断做什么、不做什么、什么时候做——比"做得快"更重要

---

## 六、一句话总结

> 这个项目最大的收获不是一套系统，而是完整经历了一次"需求质疑 → 验证 → 收敛 → 被评审打脸 → 快速修正 → 补齐闭环"的真实产品循环——**写代码可以快，但判断该做什么，永远要慢半拍。**
